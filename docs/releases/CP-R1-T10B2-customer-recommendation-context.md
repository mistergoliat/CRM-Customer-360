# CP-R1-T10B2 - Customer Recommendation Context

Branch: `feat/cp-r1-t10b2-customer-recommendation-context`, base `develop`
(contains the CP-R1-T10B1 merge, PR #75 / `8f1453b`). No commit, push or PR
was made for this task.

## Definition of Customer Recommendation

Customer Recommendation is the result of evaluating real recommendations
generated by Catalog Service's SearchProducts V2 against: the customer's
current intent, the source product, their individual purchase history, their
explicit exclusions, and the catalog's current commercial state. Its goal is
to turn product-to-product recommendations into recommendations relevant to a
specific customer, without duplicating the recommendation engine.

**SearchProducts V2 will be the base recommendation engine. Customer
Recommendation is not a new engine** - it is the layer that cross-references
SearchProducts V2's candidates with this customer's history and explicit
signals before the Sales Agent presents anything.

## Objective

Build the first internal input for Customer Recommendation:
`CustomerRecommendationContext` (`lib/brain/commercial/recommendation-context/`).
It combines Customer Profile T08 (`lib/customer-profile` purchased-products),
T09 (purchase-behavior), a source/current product, explicit conversation
exclusions, and profile availability into one deterministic snapshot, so a
later task can call SearchProducts V2, receive candidates, compare each
candidate against this context, and produce a
`CustomerRecommendationAssessment` + guidance for the Sales Agent.

**This task does not call SearchProducts V2 and does not produce
recommendations.**

## Architecture and ownership

- **Customer Profile** (`lib/customer-profile`, CP-R1-T10B1) supplies
  historical purchase facts for an already-resolved `masterCustomerId`. This
  mapper never resolves identity and never queries PrestaShop.
- **Catalog Service / SearchProducts V2** (not touched by this task) will
  generate candidates, filter, rank and explain recommendations, and remains
  the current source of truth for product name, price, stock and
  availability.
- **CRM / Sales Agent** queries both, cross-references the results with
  history via this mapper, and decides how to present them (future task).

History never creates exclusions. Repetition never creates boosts.
Explicit intent will take precedence in the future evaluation task. A
Customer Profile failure never blocks a generic (non-personalized)
recommendation - see Degradation below. This context is internal and is
never a response sent directly to the customer, nor is it copied wholesale
into a prompt.

## Inputs

`BuildCustomerRecommendationContextInput`
(`lib/brain/commercial/recommendation-context/types.ts`):

```ts
type BuildCustomerRecommendationContextInput = {
  masterCustomerId: string;
  purchasedProductsResult: CustomerProfileLookupResult<GetPurchasedProductsData>;
  purchaseBehaviorResult: CustomerProfileLookupResult<GetPurchaseBehaviorData>;
  recommendationIntent: {
    sourceProduct: ProductReference | null;
    explicitExcludedProducts: readonly ProductReference[];
    explicitRepurchaseRequested: boolean;
  };
};
```

`CustomerProfileLookupResult`, `GetPurchasedProductsData` and
`GetPurchaseBehaviorData` are imported directly from `lib/customer-profile/types.ts`
(CP-R1-T10B1) - not redefined, not renamed. The task brief referred to these as
`PurchasedProductsData`/`PurchaseBehaviorData` with a `.items` field; the real
T10B1 contract uses `GetPurchasedProductsData`/`GetPurchaseBehaviorData` with a
`.products` field, so the real names/shapes were used per "no asumir
contratos, reutilizar los tipos reales de T10B1."

`masterCustomerId` is the only identity field accepted. Email, phone, DNI and
`prestashopCustomerId` are not part of this input and are never read.

`ProductReference` is the shared identifier across the CRM/Catalog Service
boundary:

```ts
type ProductReference = { productId: number; combinationId?: number };
```

`combinationId` is the CRM/Catalog Service contract's field.
`productAttributeId` is Customer Profile's field for the same concept. The
two are equated **only** inside this mapper (`sourceProduct.combinationId`
vs. `PurchasedProductItem.productAttributeId`) - neither upstream contract is
renamed or touched.

## Output

`CustomerRecommendationContext`, `contextVersion: "customer-recommendation-context-v1"`.
Full shape in `types.ts`: `masterCustomerId`, `profileStatus`, `availability`,
`recommendationIntent` (echoed/normalized), `purchaseHistory` (`products` +
`repeatedProducts`), `sourceProductHistory`, `explicitExclusionHistory`,
`capabilities`, `warnings`.

## Historical evidence

`CustomerPurchasedProductEvidence` (from T08 `products`) deliberately drops
`productName`/`productReference` - Catalog Service is the current source of
truth for name, stock, price and links; Customer Profile only keeps the
historical facts (`productId`, `productAttributeId`, quantities, order count,
first/last purchase dates, `totalSpentTaxIncl` as a decimal string, and
`catalogStatus`, including `deleted_or_unavailable`, which is preserved and
flagged via the `purchased_product_deleted_or_unavailable` warning, not
dropped).

`CustomerRepeatedProductEvidence` is derived **exclusively** from
`purchaseBehaviorResult.data.topProducts` filtered by `isRepeated === true`.
`topVariants` is never used as a substitute. These rows are never converted
into `preferredProducts`, seeds, exclusions or boosts in this task - they are
carried through as evidence only.

Duplicate protection: two evidence rows with the same
`productId`+`productAttributeId` (or `productId` for repeated products) that
are field-for-field identical are deduplicated deterministically; if they
disagree on any metric, `buildCustomerRecommendationContext` throws
`CustomerRecommendationContextInputError` (`conflicting_purchase_evidence` /
`invalid_repeated_product_evidence`) rather than silently merging them.

## Product and variant matching

`sourceProductHistory` (section 14 of the task brief):

- `sourceProduct === null` -> `{ productPreviouslyPurchased: false, exactVariantPreviouslyPurchased: false, matchingPurchases: [] }`.
- Otherwise: `productPreviouslyPurchased` is true when any T08 evidence row
  shares `productId`. `exactVariantPreviouslyPurchased` is true only when
  `sourceProduct.combinationId` is defined **and** a row with the same
  `productId` has `productAttributeId === sourceProduct.combinationId`. A
  purchase of the same product under a different variant sets
  `productPreviouslyPurchased = true` but `exactVariantPreviouslyPurchased = false`.
  `matchingPurchases` returns normalized, deduplicated `{ productId,
  combinationId }` references only - never the full evidence row (no
  quantities/amounts leak through this field).

## Explicit exclusions

`recommendationIntent.explicitExcludedProducts` comes only from the future
caller (an explicit customer statement or explicit commercial rule) - this
mapper never invents one. It is validated, deduplicated, and sorted
(`productId` asc, then `combinationId` absent-first ascending).
`explicitExclusionHistory.matches` is the **subset of that same normalized
list** that also happens to match a historical purchase - it never adds a
purchase-derived entry that wasn't already an explicit exclusion.

## Explicit repurchase

`explicitRepurchaseRequested` is transported unchanged. It does not affect
ranking, history, exclusions, or warnings in this task - confirmed by a
dedicated test that runs the same input with the flag `true` and `false` and
asserts every other output field is identical. A future task may use it to
permit an explicit repurchase despite prior-purchase evidence
(`allow_explicit_repurchase`), but this task only carries the signal.

## Capabilities

```ts
capabilities: {
  canAssessProductHistory: purchasedProductsResult.status === "available";
  canAssessRepeatBehavior: purchaseBehaviorResult.status === "available";
  canGenerateGenericRecommendationLater: true; // always true
}
```

`canGenerateGenericRecommendationLater` is always `true`, formalizing that a
Customer Profile failure is never equivalent to a blocked generic
recommendation - the mapper always returns a valid context for every
legitimate upstream state, it never throws for a legitimate Customer Profile
state (`not_found`/`not_linked`/`degraded`/`failed` all resolve to a valid
context, never an exception).

## Profile state composition

`profileStatus` (`lib/brain/commercial/recommendation-context/buildCustomerRecommendationContext.ts#composeProfileStatus`):

- Both `available` -> `available`.
- Exactly one `available` -> `partial` (all available evidence is kept).
- Both the same non-available status -> that status.
- Both non-available but different -> resolved by fixed precedence
  `customer_not_found > customer_not_linked > degraded > failed`, plus
  warning `inconsistent_customer_profile_status`.

Section 13's empty-history rule is layered on top: if T08 is `available` with
an empty `products` list, `no_purchase_history` is added. If, additionally,
T09 is `available` with a non-empty `topProducts` (contradicting "no
purchases"), `profileStatus` is downgraded to `partial` and
`inconsistent_purchase_history` is added, even though both raw statuses were
`available`. Conversely, T08 having purchases while T09's `topProducts` is
empty is **not** treated as an error (may simply be a presentation-limit
artifact of T09) - `canAssessRepeatBehavior` depends only on
`purchaseBehaviorResult.status === "available"`, not on `topProducts` being
non-empty.

## Determinism

Pure function: zero IO, fetch, SQL, `Date.now`, random, env or logs; never
mutates its inputs (verified with `Object.freeze`d input arrays). Same input
always produces the same output, including under input array reordering.
Sort order: `purchaseHistory.products` by `lastPurchasedAt` desc, then
`productId` asc, then `productAttributeId` asc.
`purchaseHistory.repeatedProducts` by `daysSinceLastPurchase` asc, then
`orderCount` desc, then `productId` asc. `explicitExcludedProducts`,
`matchingPurchases` and `explicitExclusionHistory.matches` by `productId`
asc, then `combinationId` absent-first ascending. `warnings` follow a fixed
priority constant (`WARNING_PRIORITY`), never the order in which they were
triggered internally.

## Security

The output never contains customer name, email, phone, DNI, address,
`productName`, `productReference`, API keys, internal URLs, or an upstream
error body/stack - verified by a dedicated test asserting a secret
`productName` injected into T08 input never appears in the serialized
output. It can contain `masterCustomerId`, `productId`, `productAttributeId`,
`combinationId`, historical metrics, dates and warnings.
`CustomerRecommendationContextInputError` carries only a closed `code` (also
used as `message`) - it never serializes the offending payload, also
verified by a dedicated test. **This context is internal**: it must never be
sent directly to the customer nor copied wholesale into the final prompt.

## Degradation

`purchasedProductsResult`/`purchaseBehaviorResult` in `degraded` or `failed`
are never conflated with an empty/absent purchase history - `no_purchase_history`
is only added when T08 is `available` with a genuinely empty list, and
`degraded`/`failed` states report `purchaseHistory.products` /
`repeatedProducts` as empty *because the mapper cannot assess them*
(`canAssessProductHistory`/`canAssessRepeatBehavior` are `false`), not
because "the customer has no history." Both endpoints failing still returns a
valid `CustomerRecommendationContext` (`profileStatus: "failed"`,
`canGenerateGenericRecommendationLater: true`), never a thrown error - this
mapper only throws `CustomerRecommendationContextInputError` for malformed
*input shapes*, never for a legitimate upstream Customer Profile state.
